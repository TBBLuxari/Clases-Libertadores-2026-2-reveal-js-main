Sistemas de input
Input.GetAxis da un valor entre -1 y 1,
y lo suaviza solo: acelera y frena un poco al presionar y soltar
Input.GetAxisRaw hace lo mismo,
pero sin suavizar: siempre da exactamente
-1, 0 o 1 
float h = Input.GetAxis("Horizontal");     // suavizado
float hRaw = Input.GetAxisRaw("Horizontal"); // instantáneo
Un personaje que necesita controles precisos, tipo plataformas,
¿con cuál de los dos se sentiría más "exacto"?

Con GetAxisRaw: responde de inmediato, sin ese pequeño retraso de aceleración/frenado.
GetKey, GetKeyDown, GetKeyUp 
Input.GetKey(KeyCode.Space);     // true MIENTRAS está sostenida
Input.GetKeyDown(KeyCode.Space); // true solo en el cuadro que se presiona
Input.GetKeyUp(KeyCode.Space);   // true solo en el cuadro que se suelta
GetKey se repite en cada cuadro mientras la
tecla sigue abajo:
sirve para moverse, mientras la sostienen
GetKeyDown avisa una sola vez, justo en el instante en que la presionan:
sirve para saltar, disparar, o cualquier acción que no debe repetirse sola
Por qué importa la diferencia
Si usan GetKey para saltar por error,
el personaje va a intentar saltar
en cada cuadro que mantengan la tecla apretada
GetButton vs GetKey
Input.GetButtonDown("Jump") lee un nombre configurable,
definido en Edit → Project Settings → Input Manager
Input.GetKeyDown(KeyCode.Space) lee una tecla fija:
más directo, pero el jugador no puede reasignarla sin tocar código

Cómo usar los scripts de hoy
Cada script que muestro es el archivo completo:
borran todo el contenido de su script y pegan.
El nombre después de class tiene que ser igual al nombre del archivo: MovimientoCubo 
using UnityEngine;

public class MovimientoCubo : MonoBehaviour
{
    public float velocidad = 5f;
    public float velocidadRotacion = 90f;

    void Update()
    {
        float horizontal = Input.GetAxis("Horizontal");
        float vertical = Input.GetAxis("Vertical");
        Vector3 direccion = new Vector3(horizontal, 0f, vertical);

        transform.position += direccion * velocidad * Time.deltaTime;

        if (Input.GetKey(KeyCode.Q))
            transform.Rotate(Vector3.up, -velocidadRotacion * Time.deltaTime);
        if (Input.GetKey(KeyCode.E))
            transform.Rotate(Vector3.up, velocidadRotacion * Time.deltaTime);
    }
}
position: la más directa. Suman al lugar donde está, en los ejes del mundo.
Q y E giran el cubo, como la clase pasada

Al tablero · con forward
using UnityEngine;

public class MovimientoCubo : MonoBehaviour
{
    public float velocidad = 5f;
    public float velocidadRotacion = 90f;

    void Update()
    {
        float vertical = Input.GetAxis("Vertical");

        transform.position += transform.forward * vertical * velocidad * Time.deltaTime;

        if (Input.GetKey(KeyCode.Q))
            transform.Rotate(Vector3.up, -velocidadRotacion * Time.deltaTime);
        if (Input.GetKey(KeyCode.E))
            transform.Rotate(Vector3.up, velocidadRotacion * Time.deltaTime);
    }
}
Ojo, no es lo mismo que Translate con Space.Self
Translate con direccion completo también puede moverse de lado (input horizontal).
forward por sí solo únicamente avanza o retrocede
Una forma nueva: MoveTowards
Todo lo anterior mueve "tanto por segundo",
sin saber si hay un destino.
Si se pasan del punto,
no pasa nada: siguen de largo
Vector3.MoveTowards es distinto: recibe un punto objetivo,
y se detiene exactamente ahí, sin pasarse 
using UnityEngine;

public class MovimientoCubo : MonoBehaviour
{
    public float velocidad = 5f;
    public Transform objetivo; // arrastran aquí el GameObject punto, desde el Inspector

    void Update()
    {
        if (objetivo == null) return; // si no han arrastrado el punto, no hace nada

        transform.position = Vector3.MoveTowards(
            transform.position, objetivo.position, velocidad * Time.deltaTime);
    }
}
¿En qué situación les serviría más MoveTowards que sumar a position?
Piensen en un enemigo, o un objeto que se activa por evento

Cuando hay un destino fijo: un enemigo persiguiendo un punto, una puerta que se abre hasta cierta posición.
position += siempre suma, sin saber si hay destino: puede pasarse
Translate igual que position, con la opción de moverse relativo (Space.Self)
forward atajo: moverse hacia donde el objeto mira ahora mismo
MoveTowards se mueve hacia un punto y se detiene solo al llegar

Ahora sí: física real, con Rigidbody
Todo lo que hicimos hasta ahora mueve el Transform directo:
Unity no simula nada, solo dibuja el objeto donde le digan
Rigidbody es el Component que prende la simulación física:
gravedad, masa, choques con fuerza real
Al tablero · agregar Rigidbody

En el Inspector del cubo: Add Component → Rigidbody
Apenas lo agreguen y le den Play, el cubo se cae solo.
¿Por qué, si no escribieron ni una línea de código?

El Rigidbody trae gravedad activada por defecto: apenas existe, la física empieza a actuar sobre él.
Antes de mover nada, esto tiene que existir en la escena
El piso con su Collider,
y el cubo con Box Collider + Rigidbody.
En el Rigidbody dejen todo por defecto: Mass 1, Use Gravity activado, Is Kinematic desactivado
Problema que van a ver
Un Rigidbody es un objeto físico de verdad: si lo empujan, la fricción con el piso
lo frena por abajo y el cubo se voltea o rueda, en vez de caminar
Solución: congelar la rotación
Un personaje no debe volcarse. Hay dos formas de decirle a la física que no lo gire:

En el Inspector: Rigidbody → Constraints → Freeze Rotation: X, Y y Z marcados

O por código: rb.freezeRotation = true;
Regla importante
Con Rigidbody en el objeto, nunca muevan transform.position directo en Update:
eso pelea contra la física y puede atravesar paredes
En vez de eso, hay dos formas de mover un Rigidbody:
MovePosition y AddForce
Rigidbody.MovePosition 
using UnityEngine;

public class MovimientoCubo : MonoBehaviour
{
    public float velocidad = 5f;

    private Rigidbody rb;
    private Vector3 direccion;

    void Start()
    {
        rb = GetComponent<Rigidbody>();
        rb.freezeRotation = true;
        rb.interpolation = RigidbodyInterpolation.Interpolate;
    }

    void Update()
    {
        float horizontal = Input.GetAxis("Horizontal");
        float vertical = Input.GetAxis("Vertical");
        direccion = new Vector3(horizontal, 0f, vertical);
    }

    void FixedUpdate()
    {
        rb.MovePosition(rb.position + direccion * velocidad * Time.fixedDeltaTime);
    }
}
Se ve casi igual a mover position a mano, pero con una diferencia clave:
Unity respeta las paredes en el camino, no las atraviesa
Ojo con esto
El input se lee en Update(), cada cuadro,
pero el movimiento físico se aplica en FixedUpdate():
la física corre en su propio paso de tiempo, separado del resto del juego
Dos líneas del Start que no son de adorno
freezeRotation: evita que el cubo se voltee.
interpolation: suaviza el movimiento entre pasos de física,
para que no tiemble si la cámara es hija del cubo
Update() corre según los FPS de cada máquina.
¿Por qué la física necesita su propio "reloj" aparte?

Para que la simulación sea consistente entre máquinas: FixedUpdate corre a intervalos fijos, sin importar cuántos FPS tenga el juego.
Rigidbody.AddForce 
using UnityEngine;

public class MovimientoCubo : MonoBehaviour
{
    public float fuerza = 20f;

    private Rigidbody rb;
    private Vector3 direccion;

    void Start()
    {
        rb = GetComponent<Rigidbody>();
        rb.freezeRotation = true;
        rb.interpolation = RigidbodyInterpolation.Interpolate;
        rb.linearDamping = 4f;
    }

    void Update()
    {
        float horizontal = Input.GetAxis("Horizontal");
        float vertical = Input.GetAxis("Vertical");
        direccion = new Vector3(horizontal, 0f, vertical);
    }

    void FixedUpdate()
    {
        rb.AddForce(direccion * fuerza);
    }
}
Con AddForce ustedes no dicen dónde debe terminar:
le aplican una fuerza, y la física decide cómo reacciona (acelera, tiene inercia, se resbala)
La línea nueva: linearDamping
Es el "freno del aire". Sin ella, el cubo sigue acelerando y nunca frena.
Con linearDamping = 4 alcanza una velocidad máxima y se detiene al soltar las teclas.
MovePosition control directo: le dicen a dónde ir, y respeta colisiones
AddForce comportamiento más realista: inercia, aceleración gradual, menos control exacto
Un checkbox útil
Is Kinematic en el Rigidbody: si lo activan, ignora fuerzas y gravedad
y solo se mueve cuando ustedes lo mueven. Empuja a los objetos con física,
pero un muro quieto ya no lo frena: lo atraviesa

Una tercera opción: Character Controller
Rigidbody simula física completa: perfecto para cajas, pelotas,
objetos que ruedan o se resbalan. Pero un personaje casi nunca necesita eso
Unity tiene un Component hecho específicamente para personajes:
Character Controller
Detecta colisiones con paredes, piso y pendientes,
sin simular física real: no tiene masa, no rebota, no se cae de lado
Al tablero · agregar Character Controller

Quiten el Rigidbody y el Box Collider, y agreguen
Add Component → Character Controller
(trae su propio collider en cápsula)
Ajusten la cápsula para que quede del tamaño del cubo
En el Character Controller: Center (0, 0, 0), Radius 0.5, Height 1 
using UnityEngine;

public class MovimientoCubo : MonoBehaviour
{
    public float velocidad = 5f;

    private CharacterController controller;

    void Start()
    {
        controller = GetComponent<CharacterController>();
    }

    void Update()
    {
        float horizontal = Input.GetAxis("Horizontal");
        float vertical = Input.GetAxis("Vertical");
        Vector3 direccion = new Vector3(horizontal, 0f, vertical);

        controller.Move(direccion * velocidad * Time.deltaTime);
    }
}
Ustedes controlan el movimiento exacto, como con position,
pero Unity respeta paredes y piso automáticamente, sin código extra
Ojo con esto
Character Controller no aplica gravedad solo:
si quieren que caiga, hay que sumarla ustedes mismos, cuadro a cuadro 
using UnityEngine;

public class MovimientoCubo : MonoBehaviour
{
    public float velocidad = 5f;
    public float gravedad = -20f;

    private CharacterController controller;
    private float velocidadVertical;

    void Start()
    {
        controller = GetComponent<CharacterController>();
    }

    void Update()
    {
        float horizontal = Input.GetAxis("Horizontal");
        float vertical = Input.GetAxis("Vertical");
        Vector3 direccion = new Vector3(horizontal, 0f, vertical);

        if (controller.isGrounded && velocidadVertical < 0f)
            velocidadVertical = -2f;

        velocidadVertical += gravedad * Time.deltaTime;

        Vector3 movimiento = direccion * velocidad;
        movimiento.y = velocidadVertical;

        controller.Move(movimiento * Time.deltaTime);
    }
}
Con isGrounded sabemos si está tocando el piso.
La gravedad sube cada cuadro: velocidadVertical se vuelve más negativa
y se reinicia en cuanto aterriza
Transform puro sin colisión real: atraviesa paredes
Rigidbody física completa: gravedad, masa, choques, inercia
Character Controller colisión con el mundo, sin física completa: pensado para personajes
Para explorar más: docs.unity3d.com/ScriptReference/CharacterController
Para un jugador que camina, corre y salta, pero nunca debería
rodar como una pelota, ¿cuál de las tres conviene más?

Character Controller: es literalmente el Component pensado para ese caso.

Rotación: Euler vs Quaternion
La clase pasada rotaban con transform.Rotate(Vector3.up, ...):
por debajo, eso trabaja con ángulos
Un ángulo Euler es simplemente 3 números:
rotación en X, Y y Z. Fácil de leer y de escribir a mano 
transform.eulerAngles = new Vector3(0f, 90f, 0f);
El problema de Euler: gimbal lock
Cuando dos de esos ejes terminan alineados, se puede
perder un grado de libertad: la rotación empieza a comportarse raro, saltos inesperados
Por eso Unity no guarda la rotación real así por dentro:
usa otra representación matemática, el Quaternion
Un Quaternion representa cualquier rotación con 4 números,
de una forma que evita el gimbal lock
Tranquilos
No necesitan entender la matemática de esos 4 números:
van a construir Quaternions con funciones que Unity ya les da
Quaternion.Euler
La puerta de entrada más simple: escriben ángulos
como siempre, y Unity los convierte a Quaternion por ustedes 
transform.rotation = Quaternion.Euler(0f, 90f, 0f);
Quaternion.LookRotation
Construye la rotación exacta para que el objeto
"mire hacia" una dirección 
Quaternion rotacionObjetivo = Quaternion.LookRotation(direccion);
Muy usado para que un personaje quede mirando hacia donde se mueve,
en vez de quedar mirando siempre al mismo lado
Problema
Si asignan esa rotación directo, el giro es instantáneo:
se ve robótico, de golpe
Quaternion.Slerp: rotación suave 
using UnityEngine;

public class MovimientoCubo : MonoBehaviour
{
    public float velocidad = 5f;
    public float velocidadGiro = 8f;

    void Update()
    {
        float horizontal = Input.GetAxis("Horizontal");
        float vertical = Input.GetAxis("Vertical");
        Vector3 direccion = new Vector3(horizontal, 0f, vertical);

        transform.position += direccion * velocidad * Time.deltaTime;

        if (direccion.sqrMagnitude > 0.01f)
        {
            Quaternion rotacionObjetivo = Quaternion.LookRotation(direccion);
            transform.rotation = Quaternion.Slerp(transform.rotation, rotacionObjetivo, velocidadGiro * Time.deltaTime);
        }
    }
}
Por qué el if
Si no se están moviendo, direccion es (0,0,0):
LookRotation no puede calcular una rotación con un vector vacío
Slerp interpola entre la rotación actual y la rotación objetivo,
un poquito en cada cuadro, en vez de saltar de una a otra
¿Por qué existe Slerp en vez de usar el Lerp normal de números
para interpolar rotaciones?

Slerp interpola por el camino más corto sobre la "esfera" de rotaciones posibles: un Lerp común puede dar velocidades de giro irregulares.
Para explorar más: docs.unity3d.com/ScriptReference/Quaternion
